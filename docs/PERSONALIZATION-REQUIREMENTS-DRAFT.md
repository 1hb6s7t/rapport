# 个性化关系助手：代码审核与需求对齐稿

日期：2026-09-22。状态：需求讨论稿；本轮只读审核代码，仅新增本文档，未实现新功能、训练模型或创建定时任务。

## 已确认的产品方向

1. 模型学习用户「我」的表达方式，并结合每位好友的画像调整回复。
2. 自动整理新增数据、训练和评测；评测通过后由用户确认启用候选模型。
3. 文字、表情包和图片先按发送顺序整组预览，用户确认后再发送。
4. 用户指定真实聊天证据占 85%，星座/属相只作辅助。建议辅助资料合计上限 15%，不是每个标签各占 15%。是否影响最终关系评分正在单独对齐。

总体目标：将项目扩展为「本地聊天档案 + 有来源的人物资料 + 个人表达模型 + 双模式回复 + 媒体发送 + 可评测更新」的个人助手。

新增质量要求：情绪、语义、互动指标和趋势不以简单词表/自定阈值作为最终依据，优先采用可追溯论文及许可明确的实现，并在中文微信场景验证。选型、适用范围与验收方案见 [研究依据与复现方案](RESEARCH-GROUNDED-ANALYSIS.md)。引用论文、复现方法和验证产品效果分别标注。

### 个性化之前应修复的风险

- 显式指定 `import_id` 的回复分支未校验材料属于当前好友，也未要求已校对确认，存在跨关系混用上下文的风险。自动选择最新材料的分支有相应限制。见 `api/replies.py:63`。
- 切换关系对象时，非空 profile 可能保留上一位好友的标签。见 `frontend/src/components/RelationshipPicker.tsx:72`、`frontend/src/store.ts:37`、`frontend/src/pages/Profile.tsx:25`。这是静态路径发现，尚未实机复现。
- 标签变化可能命中旧分析结果，不能保证新标签刷新报告。见 `schemas/profile.py:75`、`api/analyses.py:70`。
- 报告把总标签预算显示成实际使用权重；「N_eff≥20 时权重接近零」也与公式数值不符。见 `frontend/src/pages/Report.tsx:258`、`:293`。

以上应作为独立缺陷修复验收，不用重写关系评分核心来掩盖问题。

## 六个需求包及验收粒度

### R1：统一人物档案与出生日期

范围：用户本人及每位好友各自维护资料，不能跨好友共享私密事实。

- 出生日期允许完整年月日、仅月日、仅年份或未知；记录公历/农历、日期精度、来源、确认状态、更新时间。
- 不把未知年份补成某一年；年龄只在出生年份已知时计算。
- MBTI 记录自述/正式测评/未确认推测的来源，不把聊天推测自动写成已确认类型。
- 星座、属相可按明示规则计算并保留人工修正。农历换算需记录使用的历法来源；生肖换年口径需明确，不能简单用公历年份取模。
- 持久档案、聊天观察画像、个人表达习惯分开保存。新聊天可以更新观察，不自动篡改用户确认的生日等事实。
- 分析和回复使用统一的上下文清单，记录读了哪个档案版本、哪些资料参与、哪些因证据不足未使用。

验收：A 好友生日或标签变化只影响 A；切换到 B 无残留。生日保存、重新进入、分析、代回复都使用同一已确认版本；未知资料保持未知。

### R2：真实聊天分析与个人表达学习

- 分析依据包含已确认资料、当前上下文、相关历史、长期互动观察、用户自己的表达偏好。
- 人物分析分开呈现「资料事实」「聊天证据支持的观察」「待验证猜测」并可回到原文。
- 事实记忆用可更新的资料库/历史检索提供；语言模型训练主要学习用户自己的回复习惯。
- 训练样本由「回复前的上下文 → 用户真实回复」组成。好友发言是上下文，不混成用户的说话风格；不把未来消息放进过去样本输入。
- OCR 未校对、角色不明、残缺或重复记录不直接进入训练集。1000 条聊天不等于 1000 份合格训练样本。
- 优先用已有预训练小模型的 LoRA/QLoRA 适配器进行真正微调；模型型号、上下文长度、训练批次在本机显存/速度测试后确定。当前 OCR 显卡加速并不等于训练环境已准备好。

验收：能看到样本数量、来源、过滤理由、训练记录、适配器版本；与未微调基线对比。换好友后，表达仍像用户本人，但只使用该好友获准的事实与历史。

### R3：聊天和多媒体本地归档

- 将临时导入与长期归档分离，为归档明确配置保留期限、加密、备份和删除规则。
- 文字记录包含消息顺序、发送者、已知发送时间与精度、采集时间、来源、校对版本、关联媒体 ID。
- 提供机器可用的 JSONL、便于查看的对话页面，以及媒体目录和索引清单。
- 图片、表情包、视频通过微信正常界面的打开/下载/另存为链路取得可用原文件；OCR 只负责屏幕文字。
- 媒体记录文件类型、校验值、来源消息、可用状态。原件、缩略图、截屏副本要分清；文件过期、不可下载和格式不支持要在清单中标注。
- 表情尽量保留动画原件；视频归档原文件及必要的可选缩略图。第一版不把视频原文件直接投入语言模型训练。

验收：导出后断开微信仍能查看文字、关联图片/表情和播放已成功保存的视频；重复采集不重复入库；原件失败不伪报成功。

### R4：资料来源与 85/15 产品权重

- 建立来源目录，记录出版者/机构、链接、版本、更新时间、适用范围与可使用范围。
- MBTI 的正式解释可参考 Myers & Briggs Foundation，但只表示偏好、不是个体行为定论；官方也不支持仅据类型决定个人关系。
- 历法/生肖换算可参考香港天文台公开历法数据。历法计算的权威性不代表出生日期或生肖能可靠预测人格。
- 已确认方向：真实聊天证据 85%，星座/属相只作辅助。建议 MBTI、星座、属相及其他辅助资料共用最多 15% 的额度，资料缺失时不强行补齐；聊天明确证据与辅助解释冲突时，聊天证据优先。
- 85/15 是用户指定的产品规则，不是经心理实验验证的权重，也不是好感度或人格正确率。替换旧的 0.40/0.20/0.10 逻辑时，必须同时更新提示、报告、版本与测试，不能只换界面数字。
- 作用范围待确认：建议用于画像的辅助解释、建议与回复风格的选择，客观关系评分继续由聊天证据决定；用户也可另行明确要求将其作为关系评分的产品权重，此时必须标明是产品自定义指数。
- 在提示词里写「按 85/15 考虑」不能证明百分比真的执行。落地建议为：先过滤违反明确事实、用户边界和好友隔离的候选，再以可记录的「聊天证据适配分 / 辅助资料适配分」进行 0.85/0.15 排序。画像里的事实判断必须有聊天或已确认档案来源，辅助解释独立标注；自然语言本身不宣称能精确分成 85% 与 15%。这项算法细化仍需在实现前确定评分口径与样例。
- 可以评估资料是否改善个性化回复，但不能通过训练给缺少证据的性格因果论背书。星座/属相主要用于用户允许的文化兴趣与表达，不凭它们捏造已经发生的行为或对方真实意图。
- 权重/策略评测采用有无该资料的对照实验，看采纳率、修改量、事实错误和用户偏好；未显示增益的信号不进入事实判断。

验收：每条规则能追溯来源；资料与聊天冲突时以证据为准；关闭标签参考不会改变同一组聊天的客观计数、时间与事实。

### R5：可控的持续更新

流程：新增采集 → 去重/校对 → 归档 → 更新可检索记忆 → 构建候选训练集 → 训练 → 独立评测 → 用户确认启用 → 保留旧版回滚。

- 定期索引更新和定期模型训练采用不同频率；积累足够合格新样本且电脑空闲时才训练。
- 桌面 OCR 会操作微信窗口，必须在约定的空闲时段和授权好友范围内运行，遇到锁屏、用户操作、窗口变化则暂停。
- 定时频率、最低新增样本数、训练时间上限和资源预算，在小样本试运行后再确定；本轮不创建定时任务。
- 训练集与评测集按时间/会话切分、去除近重复，禁止把同一段聊天的重叠截屏放到两边。
- AI 未被采纳的草稿不当成正确答案。用户最终采用/修改的版本记录反馈，经过筛选才进入后续训练。
- 用表达贴合度、用户修改量、事实准确性、跨好友信息隔离、语气边界和延迟评测。训练损失下降不能直接触发上线。
- 自动产出候选模型及与旧版的比较，用户确认后才切换。失败或退化保留原模型，并支持回滚。
- 删除归档/训练数据应追踪依赖它的记忆索引和模型版本；已训练进去的内容不能承诺仅删除文件就遗忘，需要回滚或重训。

验收：能看到每轮新增了什么、用了哪批数据、模型改善或退化了什么；未经确认不改变当前回复模型；可回到上一版本。

### R6：本地/外部双模式与混合消息发送

共用：人物档案、好友隔离、历史检索、媒体库、输出结构、评测标准及用户确认发送。

| 环节 | 本地模式 | 外部 API 模式 |
|---|---|---|
| 生成 | 本地基础模型 + 个人适配器 + 本地相关记忆 | 选定供应商模型 + 经过筛选的资料、历史摘要和个人表达例句 |
| 数据处理 | OCR、检索、训练和回复均在本机；首次公开模型下载另行说明 | 每次外发明确包含哪些文字/图片，可预览、脱敏并限制范围 |
| 个性化更新 | 更新记忆与训练候选适配器，用户确认启用 | 优先更新本地记忆与提示例句；不自动把本地适配器套到供应商模型，也不自动上传全量聊天做云端微调 |
| 能力差异 | 受显存、模型大小、速度影响 | 受 API 的上下文、多模态支持、限流、费用影响 |
| 失败处理 | 明确报错或使用用户选定的本地降级方案 | 不在没有授权时替换供应商或扩大数据外发范围 |

混合消息链路：理解意图 → 检索已授权素材/微信表情候选 → 选择具体素材 → 输出有顺序的「文字 + 表情/图片」列表 → 整组预览 → 用户确认 → 核对好友 → 逐项执行 → 回显逐项结果。

- 模型只选择已验证素材 ID，不任意编造本地文件路径。第一版使用现成素材，不扩展为自动生成图片模型训练。
- 微信按关键词搜表情是否能稳定自动化，需要按客户端版本验证；不可用时提供本地素材候选，不随意点搜索结果首项。
- 预览必须显示接收人、文字、具体表情/图片及顺序；用户可替换、删除、调整后确认。
- 确认后会话已切换则停止；某项发送结果不确定时不能整组重发，避免重复消息。记录每项已发/未发/待核对状态。
- 本轮确认的发送范围为文字、表情包和图片；视频先实现归档，视频自动发送作为另行确认范围。

验收：选择「文字 + 表情 + 图片」后，用户看到的整组预览与实际顺序一致；本地模式业务数据不出网，外部模式发送内容与预览一致；不串好友、不重复发送。

## 建议实施顺序

1. **基础正确性**：修复好友隔离、标签残留、旧报告复用与权重展示；统一档案，加入生日与来源。
2. **数据与回复闭环**：长期聊天/媒体归档、按好友检索、两种模式共用上下文及整组确认发送。
3. **训练基线**：清洗与留出集、手动小样本适配器训练、评测、确认启用、回滚。
4. **自动更新**：在基线验证后加入定期采集、样本门槛、空闲训练和候选版本通知；上线确认仍保留。

每个阶段独立演示和验收，不把「下载模型」「增加提示词」「更新记忆」记作完成微调。
