# 微信混合消息与媒体原件：实现及验收状态

本模块把「预览整组」与「确认发送」分开。原有 `/wechat/fill` 仍只填入，不发送。

## 接口与操作保证

- `POST /api/dispatch/preview`：接收已校对材料的 `capture_token`、`relationship_id`、`import_id` 和有序 `items`。每项为文字，或归档素材 ID；没有本地路径、URL、shell 命令参数。此接口不操作微信。
- `POST /api/dispatch/confirm`：只接受预览返回的 `token` 与 `digest`。摘要绑定好友、窗口、材料、上下文、顺序、具体内容及媒体原件校验值。
- `POST /api/dispatch/status`：查询逐项 `pending / sent / failed / uncertain` 回执，不重发。相同确认重复提交返回原回执，进程中断也不恢复发送。
- 配对与 CSRF 为所有端点前置条件。发送时重新检查好友、材料归属、输入权限、素材原件与校验值；所有原生操作共用微信互斥锁。
- 在每项首次输入/粘贴前保存加密的 `uncertain` 回执。任何无法确定结果的项都会停止整组，后面的项保持 `pending`。没有整组自动重试。
- 输入框现有文字或媒体、聊天内容变化、焦点变化、发送按钮不唯一时停止；不覆盖用户草稿。

## 媒体能力

静态 PNG/JPEG 与有原件的 GIF 可形成有序回复。GIF 预览保留原动画，不把第一帧伪装成完整表情；发送绑定整个原件 SHA-256。微信收藏面板中的表情不能单凭关键词自动选取，本阶段只发送已明确归档的具体文件。

媒体传输使用 Windows `CF_HDROP` 文件剪贴板和 Ctrl+V。文件来自归档服务验证后的原件，在服务私有临时目录短暂解密，结束后清理；剪贴板仅在仍由此次操作拥有时清空。

媒体发送驱动要求微信输入框提供可定位的图片预览，截图像素须匹配指定原件。GIF 还须观察到两个不同的正确帧。发送后须观察到新的右侧匹配图片/动画、输入框清空且可见文字上下文未发生无法解释的变化，才能记为 `sent`。客户端不暴露所需控件时拒绝，不猜坐标点击发送。

动态图目前限 GIF；WebP 可预览、归档，但不进入原生发送驱动。原件超过20MB、120帧或累计解码像素限制时拒绝。纯色图片缺少足够识别特征，会要求手动发送。

### 微信面板中的文字搜索表情

另有一条**不依赖归档文件原件**的微信表情搜索路径，与上述 PNG/GIF 文件发送分开。代回复页在微信好友绑定有效时提供关键词输入：点击微信无障碍名称为“发送表情(Alt+E)”的按钮，进入“搜索表情”页，用输入框的 ValuePattern 原样设置关键词；只读取当前屏幕可见的搜索结果。搜索项的无障碍名称、预览缩略图和 SHA-256 连同好友绑定保留在短期选择票据中。选定一张后再次显示具体图片、来源名称和收件人；确认时重新搜索并核对同一控件、位置与像素，变化则在点击前停止。点击后只在微信消息列表出现新的媒体项且输入框为空时记为已发送，否则记为不确定，不自动重试。此路径目前独立发送一张表情，尚未并入文字／文件整组发送。

性能策略是**无障碍名称优先，小图 OCR 仅在选中且名称笼统时运行**。微信的搜索结果本身常提供“你好表情，来自…”名称；对只显示“表情，来自…”的条目，使用 PP-OCRv5 mobile 识别所选 90×90 缩略图，结果只作提示，不替用户选图。用户能看到原始缩略图再确认。搜索时对当前好友的可见聊天项生成单向摘要，确认时比较同一摘要、双重完整好友名称和空输入框；不对整个聊天窗或全部搜索结果反复 OCR。搜索关键词由微信自己的表情搜索处理；屏幕缩略图只是发送预览，不被当成已归档的原件。

原有文字／文件发送的多次聊天 OCR 前置检查，也对**像素完全相同**的聊天区域启用最长 15 秒、最多 8 帧的内存复用；任一像素变化会重新识别，缓存内容不会写入磁盘。首次启动高质量 OCR 的长耗时仍存在，这项复用只消除同一画面在一组操作中的重复推理。

本机只读实测：关键词“你好”约 4.02 秒返回 15 个可见缩略图，其中 4 个无障碍名称直接以“你好”开头；搜索过程中无发送。独立无发送 API 验收完成真实窗口捕获→合成材料确认→搜索→具名表情预览（不启动 OCR）→笼统名称表情预览（仅该小图 OCR 输出“你好”），两个预览均绑定具体缩略图校验值，全程 0 次发送。当前高质量识别器对一张 90×90 测试缩略图首次加载约 99.55 秒、预热后约 1.16 秒；mobile CPU 识别器首次约 21.45 秒、预热后约 0.34 秒。mobile 对另一张图把“泥豪”误读为“泥障”，因此 OCR 不能作为自动发送依据。以上是此机器上的小样本计时，不是全面延迟或准确率承诺。真实选图后的微信发送回执仍待单独验收。

OCR、表情搜索及发送协议受影响回归 73 项通过，前端类型检查、生产构建与 17 项现有测试通过。轻量识别器配置参考 [RapidOCR 原项目的 PP-OCRv5 mobile 示例](https://github.com/rapidai/rapidocr/blob/main/python/tests/test_rec_language.py)。

## 从微信另存为原件

- `POST /api/dispatch/media/preview` 使用当前好友的绑定与归档 `message_ref`，返回可见媒体缩略图的短期选择票据。此时不会声称拿到了原件。
- 用户明确选择与归档消息对应的图片后，`POST /api/dispatch/media/collect` 再次核对窗口、好友、当前上下文、所选图像位置与像素摘要。
- 通过正常右键「另存为」与同进程的 Windows 保存对话框取得文件，只允许写入服务创建的私有临时目录。只有文件已出现、稳定且保存对话框已关闭，才交给归档服务验证并记录 `source_kind=wechat_save_as`。
- 找不到确切媒体、下载过期、无另存为操作或系统窗口无法核对时，返回明确失败。用户仍可在微信自行另存为，再在归档页面关联上传。屏幕截图不会升级为原件。

图片文件选择对话框已被观察到，文件名编辑框 `1148` 与打开按钮 `1` 可见。但本次 Computer Use 对模态框的焦点/控件缓存不稳定，路径填写未能可靠完成；已取消对话框，恢复空草稿。因此 **静态图片、GIF、另存为原件和发送回执仍未完成真实客户端端到端验收**。单元/接口测试不等于实机发送通过。

后续已完成真实应用的预览链路：独立服务 `http://127.0.0.1:7862/acceptance-review` 经浏览器依次执行实际微信捕获、导入、确认、归档、两份素材上传及发送预览。捕获只用于保留好友/窗口/上下文绑定；首次导入前在验收内存中替换为 `Source.demo`、`origin=synthetic_acceptance_only`、`training_allowed=false` 的3条合成材料，实际私聊未进入验收归档。独立服务关闭分析与学习调度，并在服务端拒绝发送端点；页面无发送按钮。

验收材料 ID 为 `f5284985cacd98dc`，读取加密库后确认所有 `raw` 为空、所有文本均为合成验收文字。预览摘要为 `695327f9734c7dff832f9d0ea733182240573ba83a46c5d3a7ba412f57e50ed8`，三个回执全部 `pending`。PNG SHA-256 为 `c1ee4c489ae4d439eb857f87b267dd2b0aeec5213281b0aed488aeb96a30ab0b`；GIF SHA-256 为 `f12dd33202e9be24b06dcb9b07b4881927fd63a057dc969cbaff49902943c23d`。预览证明了应用链路与确切素材，不证明真实发送成功。服务重启或十分钟票据失效后，实发必须重新读取并核对新预览。

### 首次单次实发验收与后续只读修复

用户随后明确确认上述测试组。重新捕获后的执行摘要为 `bedfcccbc7146ae8931efe79a7eec8291ab4dfad6a7a2e87b5e9f560b78b3e1e`，接收人、文字及两份原件 SHA 与确认包完全相同。仅调用了一次真实发送确认接口，返回 `stopped`：第1项在会话前置核验中 `failed / wechat_contact_mismatch`，第2、3项为 `pending`。尚未进入任何项目的发送函数，0条已发送；授权已通过独占 `.spent` 文件消耗，没有重试或补发。

之后只读检查取得的标题与输入框名称都精确为「文件传输助手」，GetRootChildren 与 ControlFromHandle 两种定位路径一致，标题标签深度22，不存在持续的不同名称或遍历截断。旧回执只保存错误码，没有保存错误时的子阶段，**无法据事后状态唯一确认那次误报的根因**；不能断言用户切换了好友，也不能断言已经证明是OCR误读。Source.demo仅改变合成材料，实时上下文摘要仍独立保留，摘要不符会使用另一错误码。

修复为：发送采用 `read_dispatch_chat`，要求标题与编辑框两份完整无障碍名称一致，截屏过程中也必须维持一致；发送模式不再在标题可访问性短暂缺失时回退OCR。既有读取及只填入功能的默认行为保持不变。已前台的微信不做多余激活；错误回执增加准确阶段及名称可用/匹配布尔值，不含聊天正文或其他联系人名称。真实不同姓名仍立即停止，不使用部分匹配。

这批变更的 dispatch、visual、navigation 回归共68项通过。实机只读身份检查通过；后续完整像素与摘要前置检查因微信当时不是前台而正常停止，未为了验证而激活、填入或发送。再验收必须使用新预览和新的具体发送确认。

在获得允许恢复已核对窗口前台的指示后，完成了**修复后严格实机 preflight**：标题与输入框均精确「文件传输助手」，真正fresh capture的摘要与现场截图读回一致、输入框为空，唯一发送控件可定位。该检查直接复用发送器session的前置逻辑，但未调用 `send`，没有填入或粘贴。证据位于 `qa/rapport-wechat-acceptance/public/strict-preflight.json`。新预览摘要 `0717f89ef7df594aca02dae1006ffdf7a948f6d73dfa96b62ecf06b62d19ea5e`，合成材料 `75230738846262b2`，3项均pending；两份媒体SHA、文字、收件人及顺序与上轮相同。服务端仍禁止confirm，旧授权仍已消耗，等待对新的具体实发验收再次确认。

### 第二次单次实发验收

用户明确批准上述三项合成材料发给「文件传输助手」。登录后的新预览摘要为 `7fa04ca08bae82392b4a4753de5516bad863f120f6a447f41a7bcd5ae26f0bfb`，三项内容、顺序和原件校验值均与批准组一致；严格实机前置检查再次通过。仅调用一次确认接口，回执为 `stopped`：文字项 `uncertain / wechat_focus_changed`，PNG/GIF 保持 `pending`，单次授权已消耗，不会自动重试。

事后只读 UIA 检查发现微信输入框保留**恰好**那条合成测试文字，没有媒体草稿；发送代码中的 `wechat_focus_changed` 只可能发生在文字发送按钮 `Click` 之前的焦点断言。此次没有点击发送。已在双重完整好友名称核验后清除本次测试留下的合成草稿，输入框恢复为空；用户原有私聊内容未修改。独立回执位于 `qa/rapport-wechat-acceptance/public/result.json`。因此目前实机仍未证实文字、PNG、GIF 的成功发送。

本次 Windows 的 DirectML OCR 初始化卡在 ONNX session 创建；为验收服务增加 `RAPPORT_OCR_CPU_ONLY=1` 本机回退后可正常读取，但速度较慢。发送文字的四个焦点断言现分别记录 `text_focus_before_fill / after_recheck / after_fill / before_click` 子阶段，方便下一次区分停在哪一步，同时仍在焦点变化时立即停止。相关 dispatch 与 OCR 回归 42 项通过。再次做任何真实发送需新的具体确认。

后续无发送探测进一步发现：微信的 Qt 窗口有时在 `SetActive()` 返回成功后仍非 Windows 前台窗口。恢复逻辑现在核对真实前台句柄；若不一致，仅在核实标题栏位置属于微信后尝试激活，并再次确认。导航与 dispatch 回归 48 项通过。一次不点击发送按钮的合成文字探测因截图阶段窗口被遮挡而停止；其草稿已精确核对并清除，未进入发送。此探测没有证明完整发送流程已修复。

另一轮无发送探测在长时间本地 OCR 后因窗口调用不可用而停止；事后核对输入框为空、好友双名称一致，仍无发送按钮调用。当前显著瓶颈是该机器上的 OCR 延迟与桌面前台稳定性。把这两项实机条件解决并完成文字、PNG、GIF 的逐项回执前，P6 不计为实机验收通过。

### 2026-09-27 发送顺序调整（代码与单测，尚未实机）

第二次实发停在点击前的 `wechat_focus_changed`：填入草稿之后还要跑一次整屏 OCR，时间长到焦点可能已经移走。现在的顺序是：填入之前用 OCR 核对当前聊天和空输入框；填入之后到点击之间只做无障碍读取（两个好友名称都精确一致、输入框与发送按钮都是核对过的那个、输入框内容与预览一致），点击前把焦点放回核对过的输入框并再次确认；点击之后再用 OCR 核对回执。文字回执比较时去掉空白并做 NFKC 规范化，因为 OCR 会把一个气泡里的多行拼成一行、可能把标点变宽；内容不同仍判为不确定。
