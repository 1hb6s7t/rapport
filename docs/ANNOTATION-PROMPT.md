# 让外部 AI 先标注、你只复核：标注提示词与口径

这份文档解决一件事：你手上是**原始未标注**的聊天记录，而评测需要标签。全程手工标上千条不现实，所以流程是「外部 AI 先标 → 只复核它自己没把握的 → 你的纠正成为金标准」。

## 先说清它是什么，不是什么

| | 谁产出 | 能用来做什么 |
|---|---|---|
| **弱金** | 外部 AI 标注 | 找出「我的模型和另一个模型都不同意」的句子（最可能是真错的地方）；给你一个复核起点 |
| **金标准** | **你的纠正** | 唯一可以用来写「准确率」「一致率」这类数字的依据 |

**不要把 AI 标注的数字当成能力结论。** 两个模型互相一致只说明它们共享同样的偏见，不说明它们判断正确——项目里那条「双人裁定 kappa ≥ 0.6 才允许把数字写进 LIMITATIONS」的规矩，指的是**人**，不是模型。所以下面的提示词刻意让 AI 标注每一条的置信度并单列出「我自己也不确定」的条目，把你的复核量压到最小。

## 使用前：隐私

把聊天记录贴给任何在线服务，就意味着这段内容离开了你的电脑、可能被对方留存或用于训练。这个选择由你做，但请知道自己在做它。若不想出网，可以用本机模型（Ollama 等）跑同一段提示词。

**标注结果与本文件无关地放在 `~/.rapport/eval/`**（脚本层强制，写进仓库会被拒绝）。仓库里永远只有合成材料。

## 提示词 A：逐句语用与情绪标注（主用）

复制下面整段，替换两个尖括号处，然后把你的一段聊天记录贴在最后。

```text
你是中文对话语用标注员。任务：对下面这段聊天记录中**每一句话**标注它的语用意图与情绪。

背景：这是一对一聊天记录。<我方> 是记录的主人，<对方> 是我们关心的那个人。
只标注 <对方> 说的话；<我方> 的话标 speaker 为 "me" 并跳过标签（但可以引用它作为依据）。

标签必须**逐字**取自下面两个固定词表，不得自创、不得改写、不得翻译：

语用意图（可多选，一句话可以同时是「撒娇假生气」和「调侃」）：
  真生气 / 撒娇假生气 / 调侃 / 反讽 / 委婉拒绝 / 寻求安慰 / 信息确认 / 分享陈述 / 询问 / 观点评价 / 抱怨 / 同意接受 / 不确定

情绪（可多选）：
  不满 / 伤心 / 开心 / 担忧 / 亲近 / 混合 / 无明显情绪 / 无奈 / 惊讶困惑 / 不确定

边界（单选，指关系层面的边界，不是语气）：
  none / explicit_decline（明确拒绝了某项提议） / stop_contact（表达了不想继续联系） / safety_concern（出现安全相关信号）

硬性要求：
1. 逐字引用原文，**不要改写、不要补全、不要合并**相邻消息。宁可多切一行，不要漏。
2. 每条判断必须给出依据：引用**同一段对话里**支持这个判断的原句（可以是 <我方> 的话）。没有依据时，把标签写成「不确定」，并把 needs_review 设为 true。**禁止编造依据。**
3. confidence 只反映你自己把握多大：high / medium / low。拿不准就用 low 并把 needs_review 设为 true。**不确定是合法答案，猜不是。**
4. 不要给好感度打分，不要给建议，不要总结。只做逐句标注。
5. 如果记录超过 80 条消息，分批输出（每批 ≤80 条），每一批都是完整的 JSON。

输出格式：**只输出一个 JSON 对象**，不要解释、不要 markdown 代码块以外的文字。

{
  "annotator": "你的模型名",
  "batch": 1,
  "messages": [
    {
      "index": 1,
      "speaker": "other",
      "text": "逐字原文",
      "pragmatic_tags": ["撒娇假生气"],
      "emotions": ["开心", "亲近"],
      "boundary": "none",
      "evidence": ["同一段里支持该判断的原句"],
      "confidence": "high",
      "needs_review": false
    }
  ],
  "uncertain_summary": "一句话说明这一批里你最没把握的是哪几条、为什么"
}

聊天记录如下（格式随意，每行一句即可）：

<<在这里粘贴聊天记录>>
```

## 提示词 B：整体判读（可选，用于和产品输出对照）

用途：拿到「另一个模型怎么看这段关系」的独立判断，和产品分数、你自己的感受三方对照。**它同样不是金标准**，只是第三方意见。

```text
你是关系对话分析师。读下面这段聊天记录，给出整体判读。不要逐句标注。

1. 这段关系目前的阶段：陌生 / 初识 / 暧昧 / 确定关系 / 稳定 / 冲突修复中 / 信息不足
2. 五维判读，每维给 0–100 的整数分，并给一句依据（引用原句）：
   - 响应度：对方回应你的速度与稳定性
   - 主动性：对方主动发起、主动提问的程度
   - 投入度：对方在对话里投入的篇幅与注意力
   - 温度：关心、亲昵、幽默的密度
   - 未来指向：对方是否接住你关于见面的提议、是否谈定具体时间
3. 三个「转折点」：哪几句之后，关系的走向明显变了？引用原句并说明方向（变好/变差）。
4. 你最不确定的一项是什么？

要求：
- 只依据记录里实际出现的内容，不要根据常识补全；记录里没有的就写「记录中没有」。
- 不要给追求建议，不要评价谁对谁错。
- 明确区分「记录支持」与「你的推测」，后者要标注「推测」。

输出 JSON：{"stage": "...", "dims": {"响应度": {"score": 0, "basis": "..."}, ...}, "turning_points": [{"quote": "...", "direction": "better|worse", "why": "..."}], "least_certain": "..."}
```

## 针对微信单聊导出（含媒体）的标注口径

### 数据形态

每段关系是一个 JSON（顶层键 `session` 与 `messages`；头部元信息块的名字不限），同目录的 `media/` 装附件。每条消息的关键字段：

| 字段 | 含义 |
|---|---|
| `type` | 中文类型：`文本消息` / `图片消息` / `动画表情` / `引用消息` / `语音消息` / `视频消息` / `系统消息` / `链接消息` / `转账消息` / `小程序消息` / `聊天记录` / `文件消息` / `通话消息` / `位置消息` / `名片消息` / `音乐消息` / `其他消息` |
| `content` | 文本消息是正文；图片/表情/视频是**相对路径**（`media\images\xxx.jpg`）；语音是 `[语音转文字] …`；引用消息是正文 + `[引用 某某：…]`；其他消息多为 `<msg><appmsg…>` XML |
| `isSend` | `1` = 我发的，`0` = 对方发的 |
| `createTime` | unix 秒 |
| `emojiMd5` / `emojiCdnUrl` | 仅动画表情有 |

### 转成标注输入

不要直接贴 JSON（模型会在括号与转义上浪费注意力）。先转成逐行文本，每行带序号，我方与对方都保留（对方那行才是标注对象，我方那行是依据）：

```text
[1] 2026-05-18 20:14 我：这个周末你有空吗
[2] 2026-05-18 20:31 对方：这周有点忙，改天吧
[3] 2026-05-18 20:32 对方：[动画表情]
[4] 2026-05-18 20:33 对方：[语音] 我说的改天是真的想约，不是客气
```

（以上为虚构示例。）

### 媒体怎么办——这里必须诚实

外部模型**看不到图片/表情包/视频的内容**，只看到标记或路径。所以：

- **语音**：微信已把多数语音转写成 `[语音转文字] …`，**直接按文字标注**，不需要额外做 ASR。
- **图片 / 动画表情 / 视频**：AI 看不到画面。标注时把这些行标成 `pragmatic_tags: ["不确定"]`、`needs_review: false`、`media_unknown: true`，不要猜。
  想让它们被真正标注，只有两条路：把图片**上传**给多模态模型（一次少量，挑转折处与高频表情包），或接受"媒体未观测"。
- **系统消息 / 转账 / 通话 / 位置 / 名片**：通常是事实而非表达，标 `信息确认` 或跳过，不要当作情绪信号。

**为什么不允许猜媒体**：一份材料里媒体可能占三成，如果模型对看不到的东西给出一致但有偏的标签，评测出来的"准确率"衡量的是模型的想象，而不是它的识别能力。未观测就是未观测。

### 分批

- 每批 **≤80 条**，且每批开头**重复上一批最后 3 条**作为上下文（否则对话在批边界处断裂，首条必错）。
- 只在批内保持连续；跨批不要重排、不要跳行，序号必须与输入一致。
- 输出 JSON 时把 `batch` 写成批号，并保留 `uncertain_summary`。

### 大材料不要靠手工贴

几万条的量级（9 段私聊、数万条消息）必须走脚本：转文本 → 分批调用 → 合并 → 校验（`scripts/annotation_check.py`）。手工复制粘贴既慢又会在批边界丢上下文，而那种丢失是**静默**的——报告里看不出来，只会让准确率虚低。

### 标注者必须是另一个厂商的模型

如果被测系统将来用 DeepSeek 作主力，就不要用 DeepSeek 去标注金标准：同一个模型在同一批语料上会表现出同一套偏见，"一致"会被误读成"正确"。标注用一个厂商、评测另一个厂商，分歧点才是真信号。

## 拿回结果后做什么

1. **先跑格式校验**，别急着人工复核：
   `uv run python ../scripts/annotation_check.py --labels "C:/path/annotated.json" --material "C:/path/chat.txt"`
   它会检查标签是否越界、原文能否对上、置信度分布，并给出「需要你复核的条目」清单。
2. 只复核 `needs_review: true` 或 `confidence != high` 的条目——通常只占少数。你的纠正直接改在那个 JSON 里（改 `pragmatic_tags` 并加 `"corrected_by": "user"`）。
3. 纠正过的条目才进金标准集合；其余留在弱金里，只用来找「明显分歧」。

## 为什么标注口径要这么死

标签越自由，越容易在事后为了好看而重新解释它们。固定词表 + 逐字引用 + 强制「不确定」这三条，是为了让标注结果**在你复核时能核到原句**，也让不同时间、不同人标的标签可以比较——这正是项目对评测的要求：少说错、说了能核。
